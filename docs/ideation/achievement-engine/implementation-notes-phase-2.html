Implementation Notes — Phase 2

Achievement Engine · 2026-08-27 · Rule Engine + 9 Achievement Definitions

Window resolution — computed directly, not via getLockoutWeeks

Context
The spec's resolveEvaluationWindow pseudocode called getLockoutWeeks(lockoutWeeks, true) to derive the lockback floor, parameterized by an explicit asOf.
Decision
getLockoutWeeks is not asOf-parameterized — it always anchors on real wall-clock time internally (confirmed: no call site in the codebase passes an override date, because none exists). Used getTuesdayAnchoredWeekStart(asOf) (which is pure) plus manual week subtraction instead. Flagged by scout before the build started.
Alternative
Add an optional asOf parameter to getLockoutWeeks itself (rejected — out of this phase's file scope, and a shared utility's signature change deserves its own review, not a side effect of this phase).

Signup checkpoint resolution — full history, not latest-only

Context
The spec named getLatestSignupSnapshotForOccurrence for resolving a raid's signup data.
Decision
That function returns only the single latest-captured checkpoint (typically closest to raid time, often 0h). Consistency/Flexibility need an early checkpoint (>=96h before start) — used getSignupSnapshotHistoryForOccurrence instead, which returns every captured checkpoint for the occurrence. Using the spec's named function as written would have made those two shapes permanently unable to award anything.
Alternative
None — this was a confirmed factual correction, not a design choice.

Bucket classification — derived from match-signups.ts's real behavior, not new fields

Context
The spec invented bucket/checkpointHoursBeforeStart fields with no direct schema source, and Open Item #2 flagged that match-signups.ts routes bench/tentative/absent signups to status: "skipped", not "matched" — appearing to make Bench Credit unable to count anything.
Decision
Read match-signups.ts's resolveFamily in full: a "skipped" result (non-class className) still carries matchedPrimaryCharacterId/matchedCharacter (set to the primary character) whenever name/Discord-based family resolution succeeded — it just can't pick a specific class-matched character. classifyBucket reads result.status + the raw className to produce confirmed/bench/tentative/absent, and both "matched" and family-identified "skipped" results are included in matchedSignups — only genuinely ambiguous/unmatched signups (no matchedPrimaryCharacterId) are excluded, consistent with the Phase 1 decision. No changes to match-signups.ts itself were needed.
Alternative
Modify match-signups.ts to attempt class-independent matching for bench/tentative/absent signups (rejected — that file isn't in this phase's scope, and turned out to be unnecessary once its actual return shape was understood).

Signup resolution scoped by window, not by attendance — Bench Credit bug caught by its own test

Context
An earlier draft scoped signup-link resolution (and each signup-based scorer's window filter) to raids the family had attended within the window — reasoning that Consistency/Flexibility only ever compare a signup against attendance for the same raid.
Decision
That reasoning doesn't hold for Bench Credit: being benched means the family did not attend that raid, so scoping to attended raids made Bench Credit structurally unable to count anything — caught by its own boundary test returning 0 instead of 2. Fixed two ways: (1) buildRuleEvaluationContext now resolves signup links by the link's own startTime against the window, independent of attendance; (2) added a raidStartTime field to MatchedSignup so every signup-based scorer (Consistency, Flexibility, Bench Credit) can window-filter directly from the signup's own timestamp rather than borrowing one from an attendedRaids row that may not exist.
Alternative
Give Bench Credit a special-cased context-building path separate from Consistency/Flexibility (rejected — the uniform raidStartTime field is simpler and correct for all three).

achievement.ruleShape set at seed time, not left null

Context
A first draft of seedAchievementDefinitions left achievement.ruleShape null for rule-based achievements, reasoning the shape lives on each tier's ruleConfig instead.
Decision
Phase 1's schema comment defines ruleShape as "null = manual-grant-only achievement" — implying non-null for rule-based ones. Fixed to derive ruleShape from the definition's own tier configs (all tiers of one achievement share a shape) and set it at creation.
Alternative
None — this was a self-caught inconsistency with Phase 1's own schema intent, not a design choice.

Zone list and thresholds are illustrative, unconfirmed against real data

Context
The spec's proposed zone list (Molten Core, Blackwing Lair, Temple of Ahn'Qiraj, Naxxramas) and all numeric thresholds were explicitly marked as a first-pass proposal pending review.
Decision
Shipped mostly as proposed in achievement-definitions.ts — no real season exists yet to seed against, and the user deferred exact-number confirmation to spec-writing time (already done) rather than requesting a second round now. One value was corrected during the build: the all-time Class Breadth capstone's minDistinctClasses is 8, not 9 — Classic Horde has 8 playable classes (no Paladin), documented inline in achievement-definitions.ts. raids.zone is confirmed free text with no enum, so an exact-string mismatch against real data would silently under-count a Zone Attendance achievement — flagged here for whoever seeds real data to double-check zone strings match exactly.
Alternative
Block this phase on confirming the real zone list against the guild's actual progression (rejected — the achievement-definitions data is trivially editable later; it isn't load-bearing for the engine's correctness, which is what this phase actually proves).

Signup matching is re-run per family — deferred, not fixed, this phase

Context
The reviewer flagged that matchSignupsToCharacters (itself a full-table query over characters/accounts/users) is called once per captured checkpoint per signup link inside buildRuleEvaluationContext, and its result doesn't depend on which family is being evaluated — yet every per-family entry point (evaluateAchievementsForFamily, getNextTierProgress) re-runs it from scratch. Across a batch of families this multiplies into redundant DB round trips.
Decision
Deliberately not fixed here. Phase 2's per-family entry points are correct in isolation, and no batch-evaluation caller exists yet — Phase 4's QStash trigger is the first one, and it's the natural place to cache/hoist a shared (raidHelperEventId, startTime, checkpoint) → SignupMatchResult[] computation across the families it evaluates in one run, since that's where the actual batch shape (N families from one raid's attendee list) becomes concrete. Flagging here so Phase 4's spec accounts for it rather than repeating the same per-family redundancy at a larger scale.
Alternative
Add a process-lifetime or request-scoped cache inside achievement-rules.ts itself now (rejected — Phase 2 has no batch caller to prove the cache's invalidation/lifetime semantics against; premature without Phase 4's actual usage pattern in hand).
