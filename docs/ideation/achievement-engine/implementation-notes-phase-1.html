Implementation Notes — Phase 1

Achievement Engine · 2026-08-27 · Season + Achievement Schema + Manual Grant

Admin UI placement — new route outside /admin/*

Context
The spec's implementation steps said to build the two-step manual admin flow "same admin section" as role-editor.tsx, implying under /admin/*. Scout flagged that apps/web/src/app/admin/layout.tsx gates the entire subtree on userpermissions:manage, not per-page.
Decision
Created a standalone route at /achievements/manage with its own server-side scope check against achievement:manage specifically, mirroring admin/layout.tsx's redirect pattern but scoped correctly. An officer who holds achievement:manage but not full userpermissions:manage can now reach the page; nesting under /admin would have incorrectly blocked them, contradicting the spec's own success criterion that only achievement:manage gates the flow.
Alternative
Nest under /admin/achievements and accept double-gating (rejected — would silently narrow who can use the feature beyond what was specified) or add a bypass to admin/layout.tsx for this one subroute (rejected — more invasive, touches shared layout logic for a single page).

Season creation — added createSeason/listSeasons

Context
The spec's schema includes a season table and notes "Season 2's real start/end date is provided later... seeded as a follow-up data change once known," but named no procedure for creating one, and the admin UI needs a season to exist before a season-scoped custom achievement can be created.
Decision
Added a minimal createSeason mutation (name/startDate/endDate, achievement:manage-scoped) and a listSeasons query, both in achievement-service.ts/achievement.ts. This is additive — it doesn't change any spec-named surface — and unblocks the admin UI from being usable at all before Season 2's real dates are known.
Alternative
Require a season to be inserted directly via db:studio/a raw SQL seed before the admin UI is usable (rejected — leaves the shipped UI non-functional for its primary season-scoped use case out of the box).

Test assertion — UNAUTHORIZED, not FORBIDDEN

Context
The spec's own success criterion and "Experiment" wording both say a missing-scope call should be tested for FORBIDDEN.
Decision
Tests assert UNAUTHORIZED, matching scopedProcedure's actual implementation in trpc.ts (it throws TRPCError({ code: "UNAUTHORIZED", ... }) for both "not logged in" and "missing scope" — there is no FORBIDDEN path anywhere in this codebase's tRPC layer). Scout flagged this exact spec/reality mismatch before the build started.
Alternative
Change trpc.ts to throw FORBIDDEN for missing-scope specifically (rejected — out of this phase's scope, and would be a breaking change to every other scoped procedure in the app for the sake of matching one spec's wording rather than the wording being wrong).

awarded_by_user_id — real FK, not a bare varchar

Context
The spec's own Drizzle sketch typed this column as an unconstrained varchar(255), deferring to an Open Item ("confirm users table's PK type").
Decision
Used uuid("awarded_by_user_id").references(() => users.id, { onDelete: "set null" }), matching auth_user.id's real type (confirmed via auth-schema.ts) and the CreatedBy/UpdatedBy helper pattern every other actor-attribution column in this codebase follows.
Alternative
Ship the spec's literal unconstrained varchar and fix it in a later migration (rejected — the correct type was directly confirmable this pass, no reason to ship a known-wrong column).

Test file split — router tests vs. service tests

Context
The spec named a single test file, src/server/api/routers/__tests__/achievement.test.ts, for both scope-gating and DB-touching logic (season validation, rule-managed-tier rejection, unique-constraint mapping, mark-seen idempotency).
Decision
Split into two files: the named router file (scope gating + wiring only, mocking the whole service module) and a new src/server/services/__tests__/achievement-service.test.ts (real service logic, mocking only ~/server/db). Mocking the service module for router tests and then re-importing "the real" module in service-level tests within the *same* file collide — vi.mock affects every import of a given path in a test file, so the service-level tests were silently exercising the mocked functions instead of the real ones. This split also matches this codebase's existing convention (service tests live beside their service, e.g. raid-signup-link-matching.test.ts).
Alternative
vi.doUnmock mid-file to un-mock between describe blocks (rejected — fragile, depends on Vitest's mock-hoisting order rather than being structurally obvious). The spec's two named cmd checks (-t manual-grant, -t mark-seen) still pass against the router file alone; the service file is additional coverage the spec didn't explicitly require but the codebase's testing convention calls for.

resolveSessionPrimaryCharacterId — resolved the spec's Open Item

Context
The spec flagged as an Open Item: "confirm the exact session→primaryCharacterId resolution helper... this codebase likely already has a 'my own characters' pattern used elsewhere."
Decision
Scout located it: profile.ts's getMyProfile resolves via users.findFirst({ with: { character: { primaryCharacterId, characterId } } }), then character.primaryCharacterId ?? character.characterId (self is primary when null, matching characters.isPrimary's generated-column semantics). Implemented the same join, extracted as its own reusable function since no prior helper existed in isolation (only inlined inside getMyProfile).
Alternative
None — this was a confirmed pattern to follow, not a design choice.
