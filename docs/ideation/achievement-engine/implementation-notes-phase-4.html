Implementation Notes — Phase 4

Achievement Engine · 2026-08-27 · QStash Evaluation Trigger

Added a third publish call site the spec didn't name — raid.ts's own createRaid mutation

Context
The spec's File Changes table wires signup_link_resolved publishing into exactly one call site: POST /api/v1/raids, right after its runPostRaidCreationSignupLinking(result.raidId) call. The scout's dependency-awareness pass found a second, structurally identical call to runPostRaidCreationSignupLinking that the spec never mentions: apps/web/src/server/api/routers/raid.ts:246, inside the web UI's own createRaid tRPC mutation — the path a raid manager uses when creating a raid directly from the site rather than through Discord/Templar's v1 endpoint.
Decision
Added the same publishAchievementEvaluate(insertedRaidInfo.raidId, "signup_link_resolved") call immediately after raid.ts's own runPostRaidCreationSignupLinking call, using the identical non-throwing helper as the other two sites. Leaving this site unwired would mean a whole class of raids — anything created through the site's own admin UI instead of the v1 API — never fires the signup-link-resolved trigger, so Consistency/Flexibility achievements depending on that raid's signup snapshot would silently never evaluate for those raids. That contradicts the phase's own stated goal (evaluate wherever a crossing could occur), and the fix is additive/safe by the same idempotency argument the spec already makes for firing the other two triggers twice.
Alternative
Leave the gap and only wire the two literally-named call sites (rejected — would leave UI-created raids permanently unable to earn Consistency/Flexibility, a real functional gap rather than a stylistic one; the fix costs one line plus an import, using code already written for this phase).

Introduced a small shared publish helper, not in the spec's File Changes

Context
The spec's own route snippet inlines the qstashClient.publishJSON(...) call directly at each of its two named call sites. With a third call site added (see above), inlining the same try/catch-and-log block three times risked the non-throwing discipline drifting between copies — exactly the kind of duplication this codebase's QStash publish sites are careful about (see raid-helper-discovery/route.ts's own cancelQstashMessage helper for the same instinct).
Decision
Factored the publish + non-throwing discipline into apps/web/src/server/services/achievement-evaluate-publish.ts's publishAchievementEvaluate(raidId, trigger), imported by all three call sites (raidlog.ts, api/v1/raids/route.ts, raid.ts). Single place to get the try/catch, the NEXT_PUBLIC_APP_URL guard, and the log shape right once.
Alternative
Inline the publish call at all three sites (rejected — three copies of try/catch discipline that must never diverge is worse than one shared four-line function).

Review finding: the achievement-evaluate publish chain broke two test files under true zero-env CI conditions

Context
Review cycle 1 (critical) caught that achievement-evaluate-publish.ts imports ~/env directly. CI's Test step (.github/workflows/ci.yml:100-101) runs with zero env vars set at all — SKIP_ENV_VALIDATION is only set on the later Build step — and @t3-oss/env-nextjs's createEnv() throws synchronously the moment ~/env is imported under those conditions, regardless of whether anything inside the importing module is actually invoked. The reviewer's initial suggested fix (make qstash-client.ts's Client construction lazy, mirroring qstash-verify.ts's Receiver) was tried first and verified not to fix it — that pattern solves a different problem (next build's page-data-collection step, which runs with SKIP_ENV_VALIDATION=1 so createEnv() itself succeeds but individual secret values are undefined). Here createEnv() itself throws at import time, before any lazy construction inside the module would even matter, so that fix was reverted.
Decision
Root-caused with a direct reproduction of CI's exact condition (env -u SKIP_ENV_VALIDATION -u QSTASH_TOKEN ... npx vitest run) and fixed by mocking the actual import chain in each affected test file, following this codebase's own established convention (mock ~/server/db rather than make production code "test-import-safe") rather than inventing a new one:
  • v1/raids/__tests__/route.test.ts — mock ~/server/services/achievement-evaluate-publish (this file's contract is the Templar 201 response, not the QStash side effect).
  • achievement.test.ts — same mock, plus two more that turned out to be needed by tracing the failure one layer at a time: ~/server/db (root.ts already registers discord.ts/search.ts, both of which import the real db singleton at module scope, pre-existing and unrelated to this phase — this file simply never ran under true zero-env conditions before this review), and ~/env directly (needed one level deeper still: trpc.ts itself — unavoidably imported, since it's the router machinery createCaller is built on — imports ~/env at module scope for a try/catch-guarded, never-exercised-by-these-tests logging helper). Verified the full fix by re-running the exact zero-env repro against the whole suite: 214/214 pass.
Alternative
Make every touched production module (qstash-client.ts, achievement-evaluate-publish.ts) "test-import-safe" via dynamic import() of ~/env at call time (considered, rejected — no precedent anywhere in this codebase, and the actual fix is smaller: this file's own tests were always going to need to mock whatever they don't want touched, the same as every other router test here already does).
