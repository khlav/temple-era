## Conventions

- **Naming**: rule shapes are `snake_case` string literals (`recipe_set_threshold`) matching the Postgres enum value exactly; their TS interface is `AchievementRuleConfig<PascalCase-of-shape>` (e.g. `AchievementRuleConfigClassAttendanceThreshold`). Scorer functions are `score<PascalCaseShape>`.
- **Imports**: `~/`-prefixed absolute imports throughout `apps/web/src`; `drizzle-orm` operators (`and`, `eq`, `or`, `inArray`, `gte`, `lte`) imported by name from `"drizzle-orm"` at the top of each file — `achievement-rules.ts` currently imports `and, eq, gte, inArray, lte` (line 1) and needs `or` added.
- **Error handling**: service-layer functions throw typed errors (`AchievementServiceError` with a `code` field) for validation failures; the rule engine's per-family orchestrators isolate failures with `try/catch` returning `{ error }` in a discriminated result type (`FamilyEvaluationResult`) rather than throwing, except the singular convenience wrappers which re-throw for backward compatibility.
- **Types**: `interface` for `AchievementRuleConfig*` members (not `type`), combined into one `type AchievementRuleConfig = A | B | C...` union at the bottom of `achievement-schema.ts`. Heavy use of `Extract<AchievementRuleConfig, { shape: "..." }>` to narrow per-scorer function signatures.
- **Testing**: Vitest, colocated in `__tests__/` beside the code under test. Two established styles: (1) mocked-`db`-object + `vi.hoisted` for pure service-layer tests (`achievement-rules.test.ts`), (2) `createCaller` + fake `db`/session for tRPC router tests (`achievement.test.ts`) — `recipe.test.ts` should follow style (2), adding whatever `~/server/auth`/`~/env`/`~/server/db` module-scope mocks are needed to avoid the same import-time failures `achievement.test.ts` documents.

## Risks

- **Admin-panel bucketing order.** `groupCatalog` (line 884) checks `achievement.hidden || achievement.ruleShape === null` *before* checking `ruleShape === "class_attendance_threshold"`. The 8 tradeskill achievements were created via `createAchievement`, which always sets `hidden: true` (`achievement-service.ts:83`) — and the spec's backfill script never flips `hidden` to `false`. So after conversion these 8 will still route into `groupCatalog`'s `secret` bucket (shown under "Legendary Feats" on the All tab), *not* into a bucket resembling `classes`. The spec's own instruction (Implementation Details §5) says to filter "the full catalog" directly by `ruleShape === "recipe_set_threshold"` for the new Tradeskill tab — **not** to extend `groupCatalog`'s if/else-if chain — which is the only approach that works correctly regardless of `hidden`. The builder must not pattern-match "reuse the classes tab's bucket" literally into `groupCatalog` itself, or the new tab will show nothing (everything will have already been claimed by the `secret` bucket check). This also means these 8 achievements will keep appearing in "Legendary Feats" in addition to the new "Tradeskill" tab — consistent with success criterion 8's wording ("no extras" refers to the Tradeskill tab's own contents, not exclusivity from other tabs) but worth the builder confirming visually per the manual test checklist.
- **`selectDistinct` not yet stubbed in the test mock.** `achievement-rules.test.ts`'s `mockDb` (lines 7–18) only declares `select`, `insert`, and specific `query.*.findMany` stubs — `scoreRecipeSetThreshold`'s spec'd implementation calls `db.selectDistinct(...)`, which has no existing mock entry. The new tests will need to add a `selectDistinct: vi.fn()` (with the same `chainable()`-style return) to `mockDb`, and/or reuse `chainable()` for both `select` and `selectDistinct` return values.
- **Onyxia Cloakweaver / Best-o Resto `recipeSpellIds` are unresolved.** The backfill script's literal `ACHIEVEMENTS` map (spec §6) has two `recipeSpellIds: [/* ... */]` placeholders explicitly left for the builder to resolve via a live `SELECT recipe_spell_id, recipe FROM recipes WHERE recipe IN (...)` query against the dev DB before the script can run — this is a real open item, not a documentation gap, and blocks a working backfill run until resolved.
- **Transaction wrapping is an explicit open item.** The spec's Open Items list flags that `addRecipeToCharacter`'s insert + evaluator call transaction behavior is unconfirmed — reading `recipe.ts` in full confirms the current mutation has **no transaction wrapper at all** (no `ctx.db.transaction(...)` anywhere in the file), so the two steps (recipe insert, evaluator call) are two independent statements today. This matches the "no try/catch, no transaction, let failures surface" design already in the spec — nothing to change, just confirms the open item's answer is "no transaction, matches existing behavior."
- **`db:migrate` vs `db:push` — resolved.** `apps/web/package.json` defines both as distinct scripts (`db:migrate` = `drizzle-kit migrate`, `db:push` = `drizzle-kit push`). Since step 2 of the spec generates a real migration file via `db:generate`, the correct dev-apply command is `db:migrate` (applies the generated migration through drizzle's journal) — `db:push` would bypass the generated file and diff schema directly, defeating the point of generating it. This resolves the spec's third Open Item.
- **Decision-log cross-check**: no contradiction found between the contract's "Decisions Considered and Rejected" log and observed codebase reality — the `scoreByShape`/`db`/`primaryCharacterId` unused-params claim, the `seedAchievementDefinitions` insert-only claim, and the enum's two prior extensions are all independently verified in the files read above.

No other significant risks identified — the schema/evaluator/hook change set is narrow, additive, and the one genuine gap (Onyxia/Best-o Resto recipe IDs) is already called out as an open item in the spec itself.
