Implementation Notes — Phase 1

tradeskill-mastery-tiers · 2026-08-29 · Tradeskill Mastery Rule Engine

Backfill script — existing tier is Arcanite, not Thorium

Context
The contract and both specs assumed the 8 achievements' existing single tier was Thorium ("Current baseline Thorium holder counts...", success criteria checking `tier='thorium'`). A direct DB check during the build (SELECT a.name, t.tier FROM achievement a JOIN achievement_tier t ...) showed every one of the 8 is actually arcanite.
Decision
Stopped and asked the user directly rather than guessing, since this affects the visible tier badge of ~54 existing legitimate holders. User chose: demote the existing tier row's tier value from arcanite to thorium (keeping the same achievement_tier.id, so existing awards/awardedAt/source are untouched — only the enum value changes), and add a new Gold tier below it for the 6 graduated achievements. This matches "Gold + Thorium" literally, at the cost of a visible badge-color change for current holders on next view. Applying this via UPDATE, same technique achievement-service.ts's own updateAchievement already uses for tier-level edits without disturbing awards.
Alternative
Two alternatives were offered and declined: (1) keep the existing tier as Arcanite unchanged and name the new lower tier "Thorium" instead of "Gold" (adjacent on the tier ladder, no disruption to existing holders); (2) same but name the new lower tier "Gold" (skips Thorium entirely, two rungs below Arcanite). Both would have avoided touching already-granted award rows' visible tier.

Backfill evaluation pass — needed real batching, twice

Context
The spec's first draft of step 3 looped the singular evaluateRecipeAchievementsForFamily once per family. The user asked directly ("why wouldn't you batch with an optional per-character/family filter?") after the first live run exceeded a 2-minute timeout.
Decision
Two fixes, in order. First: added a real batched sibling, evaluateRecipeAchievementsForFamilies (plural) in achievement-rules.ts, mirroring the existing evaluateAchievementsForFamilies pattern — fetches recipe-shaped tiers and the whole batch's existing awards exactly once, not once per family. The singular function became a one-element wrapper over it (no change to the hook's call site). This is the right shape for the hook (1 family) and for moderate batches, and is the version that ships as a real, tested, reusable service export. Second: this still wasn't enough for a full-guild backfill — the per-family *scoring* itself (2 queries × tier × family) remained thousands of sequential round trips. Rather than further complicate the shared service function for a one-time bulk case, the backfill script's step 3 was rewritten as a self-contained bulk pass: one query fetching every (family, known recipe) pair across all tracked recipes at once, all threshold comparison done in memory, one batched insert for every new award. Re-run confirmed fast and correct (idempotent diff-check passed, 15 new Gold awards granted).
Alternative
Considered forcing the shared evaluateRecipeAchievementsForFamilies to handle the full-guild case efficiently too (e.g. batching the per-family scoring queries), but that would mean the shared service function optimizes for two very different call shapes (one low-frequency family vs. every family in the guild at once) at the cost of complexity neither caller fully needs. Keeping the bulk optimization script-local matches this session's existing convention of one-off scripts owning their own bulk-data-shape concerns.

Backfill idempotency — the tier-demotion UPDATE needed to be scoped to `arcanite` specifically

Context
The script's first live run was killed mid-execution (the 120s-timeout backgrounding, then an explicit stop) after already completing the tier conversion for all 8 achievements and partially granting Gold awards. A second run then failed: UPDATE achievement_tier SET tier='thorium' WHERE achievement_id=X hit a unique-constraint violation, because after the first run there were now two tier rows per achievement (the demoted thorium row and the new gold row) and the blanket update had no way to distinguish them.
Decision
Scoped the demotion UPDATE's WHERE clause to tier = 'arcanite' specifically (the known pre-conversion state), so a re-run after a successful conversion matches zero rows instead of colliding. Also fixed the pre-migration snapshot step the same way (query the arcanite row if it exists, else fall back to the now-demoted thorium row) so the baseline is correct on both a fresh run and a re-run.
Alternative
None seriously considered — this was a straightforward idempotency bug in the original design, not a genuine tradeoff.
